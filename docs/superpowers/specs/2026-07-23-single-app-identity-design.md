# Mac Face Lock 单一应用身份设计

## 背景

当前发布版同时存在用户可见的 `Mac Face Lock.app` 和内嵌的
`Mac Face Lock Agent.app`。macOS 将两者视为不同的 TCC 权限身份，因此用户必须在
摄像头、输入监控和辅助功能中分别识别两个名称。真机验收还证明了两个独立故障：

- 已经响应正常的后台任务再次安装时，会先 `bootout`，随后立即 `bootstrap`；
  macOS 可能返回错误 5，安装回滚又落入同一竞态，最终停止原本健康的后台任务。
- 安全测试由独立的 `MacFaceLockRuntime` 执行摄像头诊断。即使
  `Mac Face Lock Agent` 已获得三项权限，该 Runtime 仍可能没有可用摄像头身份，
  导致安全测试停留在“摄像头或权限不可用”。

用户确认产品应只呈现一个应用、一个菜单栏入口和一个权限身份；关闭窗口后继续
驻留，只有明确退出时才停止保护。

## 目标

- 发布包只包含一个 `Mac Face Lock.app`。
- 摄像头、输入监控和辅助功能只依赖 `com.wuyi.mac-face-lock.app`。
- 同一个 `MacFaceLock` 主程序支持界面模式和受控后台运行模式。
- 关闭窗口不退出，菜单栏和后台保护继续运行。
- 明确退出时先关闭保护并停止后台任务，再终止界面进程。
- 保留登录启动、崩溃拉起、连续心跳和严格安全门槛。
- 一次性迁移旧 Agent，完整保留人脸资料、设置、日志和历史证据。

## 非目标

- 不在本轮将 Python/OpenCV 人脸运行时重写为 Swift。
- 不降低摄像头、输入监控、辅助功能、本人资料、本人验证或后台健康门槛。
- 不自动修改 macOS TCC 数据库，也不冒充用户清理历史权限记录。
- 不改变锁屏判定策略、冷却时间和 `lock_on_camera_error=false` 的失效开放原则。

## 选定架构

### 单一应用包与单一主程序

发布产物中删除独立的 `Mac Face Lock Agent.app`、其 Bundle ID 和独立启动器。
`Mac Face Lock.app/Contents/MacOS/MacFaceLock` 成为唯一的应用入口。

主程序依据严格校验的内部参数进入两种模式：

- 无内部参数：启动 AppKit 控制中心和菜单栏。
- 参数形态为 `--internal-runtime --resources-dir <path> --support-dir <path>
  <command>`：校验命令、应用内 Resources 路径和用户应用支持路径后，
  以当前 `Mac Face Lock` 应用责任链执行本地运行时命令。

受控命令只允许 `agent`、`enroll`、`diagnose` 和 `verify-owner`。任何未知命令、
相对路径、符号链接逃逸或应用包外 Resources 路径都必须在运行时启动前拒绝。
正常用户启动永远不能意外进入后台命令模式。

Python/OpenCV 运行时仍作为 `Mac Face Lock.app` 内部资源存在，但不再作为第二个
应用或第二个权限身份发布。界面发起的录入、诊断和本人验证，以及登录任务发起的
后台保护，都通过唯一主程序的受控入口进入运行时。

### 后台任务

新的用户级 LaunchAgent 使用标签 `com.wuyi.mac-face-lock-background`，并只指向：

```text
/Applications/Mac Face Lock.app/Contents/MacOS/MacFaceLock
```

参数明确指定受控后台模式、应用内 Resources、用户应用支持目录和 `agent` 命令。
LaunchAgent 保留 `RunAtLoad` 与 `KeepAlive`，以便登录自动启动并在后台实例崩溃后
重新拉起。它不指向独立 `.app`、独立 Bundle ID 或外部源码目录。

界面实例与后台实例可以是两个进程，但两者来自同一个主程序、同一个应用包和
同一个 TCC 身份。用户和系统设置只需要识别 `Mac Face Lock`。

## 生命周期

- 打开应用：启动界面实例、显示控制中心并建立菜单栏入口。
- 关闭控制中心窗口：只隐藏窗口，应用继续驻留；后台保护不受影响。
- 点击 Dock 图标或菜单栏“打开控制中心”：重新显示现有窗口。
- 用户登录：LaunchAgent 可在不弹出控制中心的情况下启动后台模式。
- 明确选择“退出 Mac Face Lock 并停止保护”：
  1. 将 `protection_enabled` 原子写为 `false`；
  2. 停止并禁用当前后台任务；
  3. 观察到后台进程退出或报告可操作错误；
  4. 最后终止界面实例。
- 用户再次手动打开应用：幂等恢复并启用后台任务，但保护仍保持关闭，直到用户
  明确选择恢复或开启。

如果退出流程无法证明后台已经停止，界面不得静默退出；它必须保持保护关闭并向
用户显示可操作错误。

## 服务安装与幂等性

后台安装操作首先读取受管理 plist、当前 launchd 状态和新鲜心跳：

- 程序路径、参数和应用支持路径都匹配，且后台实例响应正常：保留当前 PID，
  不执行 `bootout`、`bootstrap` 或 `kickstart`。
- plist 缺失、程序路径变化、参数不匹配或后台不响应：进入可回滚的替换流程。
- 替换流程必须等待旧任务确实离开 launchd 域后再加载新任务；不能忽略
  `bootout` 结果后立即假定卸载完成。
- 任何失败都将保护保持为关闭，并恢复安装前的受管理 plist/任务状态；用户数据
  和应用包不属于服务回滚的删除范围。

重复运行安全测试、前台刷新和应用重开不得停止一个路径正确且响应正常的后台
实例。

## 首次设置数据流

1. 准备检查验证应用位置、运行组件和应用支持目录。
2. 权限中心只请求并显示 `Mac Face Lock` 的摄像头、输入监控和辅助功能。
3. 录入由唯一主程序以 `enroll` 命令启动，结果只写入本地本人模板。
4. 安全测试先保持保护关闭，再执行 `diagnose`、幂等后台确认、本人无锁验证和
   最新权限/心跳刷新。
5. 只有运行组件、本人资料、本人验证、三项权限和后台健康全部通过，才将首次
   设置推进到“完成并开启”。
6. 点击最终开启按钮前必须再次得到用户确认；此前 `protection_enabled` 始终为
   `false`。

所有运行时命令仍使用现有严格 JSON 事件协议。界面不得根据可见应用的静态权限
开关伪造后台健康；后台状态必须由匹配 PID 的新鲜、递增心跳和真实权限结果证明。

## 旧 Agent 一次性迁移

迁移只处理明确受管理的旧对象：

- 旧 LaunchAgent 标签和 plist；
- 旧发布包内嵌 Agent 路径；
- 当前应用生成的新单一身份 LaunchAgent。

迁移顺序为：保护关闭、读取并备份受管理状态、停止旧任务、写入新 plist、启动并
验证新后台、最后删除旧受管理 plist。人脸模板、配置、控制记录、日志、活动记录和
证据目录全部保留。

若发现未知程序路径、符号链接、所有者异常或无法归类的旧任务，迁移必须停止并
保持保护关闭，不得扩大删除范围。

旧 `Mac Face Lock Agent` 的历史 TCC 行可能在当前测试机上暂时保留。应用不直接
编辑 TCC 数据库；真机验收时由用户确认后在系统设置中移除或关闭旧行。新产品逻辑
和新安装只依赖 `Mac Face Lock` 三项权限。

## 界面文案

- 权限中心显示“Mac Face Lock 摄像头”“Mac Face Lock 输入监控”“Mac Face Lock
  辅助功能”。
- 删除所有“Agent 权限”“重新安装 Agent”和要求用户选择内部可执行文件的文案。
- 服务修复统一称为“修复后台保护”。
- 菜单栏退出项改为“退出 Mac Face Lock 并停止保护”，并在执行前说明保护会停止。
- 安全测试继续展示四类门槛：运行组件与数据目录、本人资料、本人验证、后台运行与
  实际权限。

## 错误处理与安全原则

- 摄像头不可用、权限缺失、本人资料无效、本人验证失败、后台 PID/路径不匹配、
  心跳陈旧或安装迁移失败时，绝不锁屏。
- 失败路径必须写入 `protection_enabled=false`，并给出面向用户的中文修复提示。
- 后台崩溃可以由 launchd 拉起，但重新启动不能自动伪造健康或跳过安全测试。
- 摄像头错误仍是失效开放，不得等同“陌生人”结果。
- 应用替换继续使用可回退原子交换；验收完成前保留旧应用副本。

## 发布包约束

最终 ZIP 中必须满足：

- 只有一个顶层 `Mac Face Lock.app`。
- 不存在 `Contents/Library/LoginItems/Mac Face Lock Agent.app`。
- 不存在 `com.wuyi.mac-face-lock-agent.app` 或 `MacFaceLockAgent` 可执行文件。
- LaunchAgent 模板只引用 `Contents/MacOS/MacFaceLock`。
- 内部运行时仍位于应用 Resources 的固定、签名覆盖路径中。
- 完整应用通过 `codesign --verify --deep --strict`。

## 测试策略

### 自动测试

- 主程序模式解析：普通启动、四个允许命令、未知命令、相对路径和路径逃逸。
- AppEnvironment 与 RuntimeCommandRunner：所有发布运行时命令经唯一主程序入口，
  源码模式保持现有开发路径。
- ServiceManager：健康同路径后台安装为无变更操作；错误路径和不响应状态仍执行
  可回滚替换；卸载完成条件受测试控制。
- SetupCoordinator：安全测试重复运行不停止健康后台；任一门槛失败都不能开启
  保护。
- 退出流程：先关闭保护、停止后台，成功后才终止；停止失败时界面保留并提示。
- 迁移：只移除旧受管理对象，未知对象阻断，人脸资料和设置字节不变。
- 打包：发布包中没有独立 Agent 应用、Bundle ID、可执行文件或路径引用。
- 运行完整 Python、Swift 聚焦套件、全量 Swift 类型检查、发布包解压测试、签名、
  校验和和自动预检。

### 真机验收

1. 安装前记录本人模板 SHA-256、首次设置状态和保护关闭状态。
2. 原子安装新发布包，保留当前和更早应用副本。
3. 确认运行进程、LaunchAgent program 和系统权限只依赖 `Mac Face Lock`。
4. 开启 `Mac Face Lock` 的三项权限，运行安全测试并确认全部变绿，推进到
   “完成并开启”。
5. 关闭窗口，验证菜单栏和后台 PID/递增心跳继续；重新打开窗口验证状态一致。
6. 明确退出，验证保护关闭、后台停止且本人模板不变。
7. 重新打开，验证后台幂等恢复但保护不会擅自开启。
8. 用户确认后开启保护，验证新鲜心跳、三项权限和本人验证保持通过，且摄像头或
   权限错误不会锁定本人。
9. 用户确认后清理当前测试机上不再使用的旧 Agent 权限行和旧应用备份。

## 验收完成定义

- 代码、自动测试、发布构建和独立审查全部通过。
- 真机安全测试可稳定进入下一步，重复运行不会破坏后台实例。
- 系统只需要授权 `Mac Face Lock`，新发布包不含独立 Agent 应用身份。
- 关闭窗口继续保护，明确退出停止保护，重新启动不擅自开启保护。
- 本人模板哈希保持不变，旧版本在用户接受最终清理前可恢复。
- Git 分支、是否合并、是否推送和是否发布分别明确；没有用户授权不得推送。
