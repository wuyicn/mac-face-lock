# Mac Face Lock 权限驱动首次设置设计

## 目标

取消会长期阻塞普通用户的“安全测试”步骤，把首次设置改成：

1. 准备检查
2. 录入本人
3. 权限状态
4. 完成并开启

录脸成功并开启必需权限后，用户可以完成首次设置并进入主界面。后台服务暂时异常时，不再把用户锁在首次设置中；应用进入主界面并明确显示“保护尚未开启”和修复入口。

## 已确认的产品原则

- 首次设置的目标是让用户完成本人人脸资料和系统权限配置，不再要求额外执行本人验证或运行诊断。
- “完成首次设置”和“保护已经运行”是两个不同状态。
- 只有后台服务真实健康时，应用才能把保护开关写为开启。
- 服务不健康时，首次设置仍可完成，但保护保持关闭，主界面进入恢复状态。
- 录脸失败、权限未开启或应用正在退出时，不能错误完成首次设置。
- 本人资料、设置和活动记录继续只保存在本机。

## 方案比较

### 方案 A：只改页面名称

把“安全测试”改名为“权限状态”，但保留原有诊断、本人验证和服务健康门槛。

优点：改动少。

缺点：用户仍会卡在同一个后台门槛，只是文案不同，不能解决当前问题。

### 方案 B：权限驱动完成，服务状态非阻塞（采用）

移除安全测试步骤。完成首次设置只要求：

- 本人人脸资料有效；
- 摄像头权限已开启；
- 输入监控权限已开启；
- 辅助功能权限已开启；
- 若用户启用了截图证据，再要求屏幕录制权限。

完成时尝试安装或恢复后台服务。服务健康则开启保护；服务失败则完成首次设置、进入主界面并保持保护关闭。

优点：符合用户确认的流程；不再把产品启动与后台服务稳定性混成一个门槛；仍保持“未健康不启用保护”的安全边界。

缺点：主界面必须清楚区分“设置完成”和“保护运行中”。

### 方案 C：权限齐全后无条件开启保护

不检查后台服务健康，直接把保护开关写为开启。

优点：流程最短。

缺点：界面可能显示已开启，但服务并未运行，属于错误安全承诺，因此不采用。

## 首次设置流程

### 1. 准备检查

保留当前硬件、系统版本、应用位置、运行组件和本地目录检查。通过后直接进入“录入本人”，不先停留在独立权限页。

### 2. 录入本人

页面同时显示摄像头权限状态：

- 未决定：按钮触发 Mac Face Lock 摄像头权限请求；
- 已拒绝：显示“打开系统设置”；
- 已开启：允许开始录入。

录入成功并安全保存本人模板后，直接进入“权限状态”。

### 3. 权限状态

显示以下状态与系统设置入口：

- 摄像头；
- 输入监控；
- 辅助功能；
- 屏幕录制，仅在截图证据功能开启时标为必需。

页面每两秒刷新一次权限状态。必需权限全部开启后，“继续”按钮可用并进入“完成并开启”。

页面只展示当前统一 Mac Face Lock 应用身份的权限，不再展示已经取消的安全测试、本人验证、运行诊断或测试进度。

### 4. 完成并开启

页面显示：

- 本人人脸资料；
- 摄像头权限；
- 输入监控权限；
- 辅助功能权限；
- 可选的屏幕录制权限；
- 后台服务状态，标记为“运行中”或“将在进入主界面后修复”。

用户点击“完成并开启”后：

1. 再次读取权限和本人资料；
2. 若必需权限或本人资料缺失，留在当前页并指明缺失项；
3. 先把保护保持为关闭；
4. 持久化首次设置已完成；
5. 尝试安装、启动或恢复后台服务；
6. 服务健康时开启保护；
7. 服务未健康时保持保护关闭，并进入主界面恢复状态。

该按钮不得运行旧的 `diagnose` 或 `verify-owner` 安全测试。

## 状态模型与兼容迁移

新的活动步骤集合为：

- `preparation`
- `enrollment`
- `permissions`
- `completion`

旧记录兼容规则：

- 旧 `current_step = safety_test` 映射到 `permissions`；
- 旧记录停在 `permissions` 且没有有效本人资料时，恢复到 `enrollment`；
- 有效本人资料存在时，恢复到 `permissions`；
- 已完成的旧记录继续保持完成，不强制重做首次设置；
- 旧 `completed_steps` 中的 `safety_test` 在读取时归一化为 `permissions`，保存时不再写入 `safety_test`；
- 恢复路径中原来指向安全测试的情况改为权限状态或主界面恢复状态。

迁移必须兼容现有 schema 1 数据，不能删除、覆盖或重新录制本人资料。

## 安全边界

移除安全测试不代表放宽以下边界：

- 录入开始前保护必须关闭；
- 退出或取消时，迟到的运行组件结果不能提交；
- 本人模板写入继续使用原子替换和安全回滚；
- 缺少必需权限时不能完成首次设置；
- 后台服务未被权威确认健康时，不能把保护写为开启；
- 任何服务修复失败都保持 fail-open，不触发锁屏；
- 旧版清理门槛、plist 校验、文件绑定和回滚防竞态保持不变。

## 主界面行为

首次设置完成后，根界面根据真实运行状态进入：

- `mainReady`：服务健康且保护已开启；
- `mainRecovery`：首次设置已完成，但服务或权限需要修复。

`mainRecovery` 必须清楚显示：

- “首次设置已完成”；
- “保护尚未开启”；
- 当前缺失权限或后台服务问题；
- 刷新权限、打开系统设置、重新安装或重启服务的入口。

不能把“已完成设置”呈现为“保护已运行”。

## 测试设计

实施遵循测试先行，至少覆盖：

1. 新步骤顺序不包含安全测试；
2. 旧 `safety_test` 记录可迁移且不损坏已完成人脸资料；
3. 无本人资料时不能越过录入；
4. 录入成功后进入权限状态；
5. 必需权限缺失时不能完成；
6. 必需权限和本人资料齐全时可以持久化完成；
7. 服务不健康时完成设置但保护保持关闭，并进入恢复主界面；
8. 服务健康时完成设置并开启保护；
9. 完成按钮不调用 `diagnose` 或 `verify-owner`；
10. 退出、取消、旧版清理和本人模板回滚安全测试继续通过；
11. UI 和公开文档不再把“安全测试”列为首次设置步骤；
12. 完整 Swift、Python、发行包和安装前数据指纹验证通过。

## 验收标准

- 新用户录完本人、开启必需权限后可以完成首次设置；
- 页面不再出现“运行安全测试”按钮；
- 后台服务异常不会把用户卡在首次设置；
- 服务异常时主界面显示保护未开启，而不是虚假成功；
- 服务恢复健康后可以开启保护；
- 旧用户资料和旧完成记录保持有效；
- 安装新版前后本人模板和配置指纹一致。
